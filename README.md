# Scaffolding

A minimal TanStack Start template for new projects: server-rendered React pages,
strict TypeScript, a restrained responsive design, and Vercel deployment support.

## Start

Use Node.js 24 and Bun 1.3.5 (pinned in `package.json`). From this directory:

```sh
bun install
bun run dev
```

Open http://localhost:3000. `/` is the sample landing page; `/about` is a second
server-rendered page with a short setup guide. Unknown URLs have a real 404 status.

## Make it yours

- `src/routes/index.tsx` and `about.tsx`: replace the sample pages.
- `src/lib/site.ts`: update the project name, description, and metadata helper.
- `src/styles.css`: change colors, typography, and layout with plain CSS.
- `public/favicon.svg`: replace the sample mark.
- `AGENTS.md`: development rules for future coding agents and contributors.

Copy `.env.example` to `.env` and replace `https://example.com` with your real
production origin. `VITE_SITE_URL` is optional for local development; when unset,
canonical and `og:url` tags are omitted. It is a **public build-time variable**:
set it in Vercel before building, and redeploy after changes. Never put secrets
in variables prefixed with `VITE_`.

The project uses system fonts, local SVG, and no UI framework, database, auth,
analytics, or state library. Add these only when your project needs them.

## Check and preview

```sh
bun run check       # Lint and formatting
bun run build       # Production build and generated route types
bun run typecheck   # Strict TypeScript check
bun run test        # Real HTTP checks against the production build
bun run start       # Serve the production build at localhost:3000
```

`bun run format` fixes formatting and safe lint issues. `src/routeTree.gen.ts` is
generated by TanStack during development/build; keep it committed and do not edit it.

## GitHub and Vercel

For each new project, copy **the contents of `scaffolding/`**, including dotfiles,
into a new repository root. Create a **private** GitHub repository and create/link
the matching Vercel project through the CLI. With GitHub CLI and Vercel authenticated,
run from the new folder (replace `my-project` with the chosen project name):

```sh
git init -b main
git add .
git commit -m "Initial scaffold"
gh repo create my-project --private --source=. --remote=origin --push
bunx vercel link
bunx vercel git connect
```

In `vercel link`, choose to create a new project with the matching name. You can
also enable **Template repository** in GitHub settings to reuse it through
**Use this template**. Keep new repositories private. The included GitHub workflow
checks every pull request and pushes to `main`.

Configure the linked project in Vercel:

1. Select the **TanStack Start** framework and **Node.js 24**.
2. Leave the root directory at the repository root. If deploying this parent
   repository directly, set the Vercel root directory to `scaffolding` instead.
3. `vercel.json` supplies `bun install --frozen-lockfile` and `bun run build`.
   Leave Vercel's output-directory setting at its framework default.
4. Add `VITE_SITE_URL` with your production origin and deploy.
5. Connect your domain and test the deployed URL, including direct `/about` requests.

Nitro detects Vercel and produces its Build Output API structure. To verify that
target locally on macOS/Linux:

```sh
NITRO_PRESET=vercel bun run build
```

This creates `.vercel/output/`. Run a normal `bun run build` again before local
`bun run start` or `bun run test`. The CI workflow does both builds.

If `scaffolding` stays inside a parent repository, GitHub does not discover its
nested `.github` folder. Move the workflow to the repository root and set its
working directory and Bun setup package path to `scaffolding`.

Framework versions are pinned for repeatable installs. This version of TanStack
Start's documented Vercel integration uses **Nitro 3 beta**; update the framework
and adapter deliberately and rerun both build targets.

## PageSpeed

The baseline includes full SSR, automatic route splitting, intent preloading,
compressed static assets, small CSS, system fonts, reserved illustration space,
unique metadata, a favicon,
and `robots.txt`. There are no external font/image requests or third-party scripts.

To measure locally, run `bun run build && bun run start`, then in another terminal:

```sh
bunx lighthouse http://localhost:3000 --output=html --output-path=lighthouse-report.html --view
```

Lighthouse requires Chrome. This audits the production app with mobile defaults.
After deployment, run [PageSpeed Insights](https://pagespeed.web.dev/) on both routes.
Aim for 90+ mobile performance and 100 accessibility, best practices, and SEO;
recheck when you add images, fonts, scripts, or data fetching. Local Lighthouse
results are lab measurements, not a guarantee of real-user Core Web Vitals.

Before a real launch, replace all sample content, configure the production URL,
add a social sharing image if needed, and add a sitemap when there are indexable
content routes to maintain. Protect private previews through Vercel.
